# 小懿双模式 Harness 与六系统协同实施方案

日期：2026年10月29日。状态：待用户审阅，实施在用户确认后开始。

目标是将小懿建设为六系统共用的任务入口：理解指令、生成有依赖关系的步骤、调用实际业务能力、核验结果，并支持策略比较和研究。两种模式共用执行底座、身份权限、数据口径、约束检查和审计机制。企业受控模式侧重业务任务完成，RL策略研究模式侧重候选策略的可复现实验。

本轮只开展公开资料和本地代码的只读核查，并新增这份方案。尚未下载模型权重、安装依赖、修改运行代码、启动训练或操作下游系统。下文的实施步骤和验收数值均为拟定目标。

## 1 技术路线与模型选型结论

推荐采用“保留小懿现有模型和功能，按需接入规划模型及业务策略”的路线。Harness 是执行和治理软件；大语言模型负责理解与规划；业务策略负责路径、资源或能源等数值决策。这三部分可以分别升级。

已经找到可下载的预训练权重，因此第一步应验证复用。现有公开候选覆盖任务规划、车辆路径和运输任务分配等子问题；本次没有确认到能够直接理解小懿全部接口并完成六系统所有业务的通用港航策略。

### 1.1 开源候选

| 候选 | 已确认的发布内容 | 拟接入位置 | 主要适配条件 | 初步优先级 |

| LangGraph | MIT开源流程框架，提供持久化和人工中断机制 | 执行机制的比较参考或局部复用 | 与现有任务存储、审批和恢复机制兼容 | 不默认重写现有Harness |

AgentCPM-Explore的论文与官方模型页支持上述模型规模和训练背景；其公开研究任务表现不能替代港航业务验收。[论文](https://arxiv.org/abs/2602.06485)、[官方模型](https://huggingface.co/openbmb/AgentCPM-Explore)、[官方GGUF](https://huggingface.co/openbmb/AgentCPM-Explore-GGUF)。

RouteFinder支持多种VRP问题，官方提供下载及测试流程。把它用于港区运输是本方案的适配方向，具体适用性需要验证。[模型与使用说明](https://huggingface.co/ai4co/routefinder)、[官方代码](https://github.com/ai4co/routefinder)。

PARCO代码提供异构容量车辆路径、开放式多仓取送和柔性流水车间示例；首期只使用已经确认存在的HCVRP检查点，不假设所有示例都有现成权重。[官方代码](https://github.com/ai4co/parco)、[官方权重](https://huggingface.co/ai4co/parco)。

LangGraph可作为持久化和人工介入机制的参考；Agent Lightning用于模型训练，两者都不等同于已训练的港航策略。[LangGraph持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[人工中断](https://docs.langchain.com/oss/python/langgraph/interrupts)、[Agent Lightning](https://github.com/microsoft/agent-lightning)。

### 1.3 复用与训练的决策条件

1. 先验证小懿现有模型能否满足限定任务的工具调用要求。
2. 如果现有模型在任务规划上存在明确不足，隔离测试AgentCPM-Explore；通过相同任务集比较后再决定是否启用。
3. 业务策略先审计已有模型，再测试适配的开源检查点。能够满足约束和效果要求的候选直接复用。
4. 发现任务语义不匹配、约束不支持、推理资源不适配，或效果未达到预先声明的标准时，记录失败原因，再训练相应的小型业务策略。
5. 首期训练目标是港航业务策略，不包含从头训练大语言模型。后续只有在轨迹和基准证明规划模型需要训练时，才单列Agentic RL或LoRA项目及算力预算。

下载成功、推理成功、业务准入和生产准入分别记录。开源策略在研究模式中可以保留为未通过准入的比较对象；业务模式只能调用已通过相应任务验收的版本。

## 3 两种模式的运行方式

| 设计项 | 企业受控模式 | RL策略研究模式 |
| --- | --- | --- |
| 入口 | 自然语言、任务模板、移动端任务请求 | 自然语言研究目标、实验模板 |
| 计划 | 受约束步骤及依赖关系 | 实验设计、基线、候选、数据范围和评测方法 |
| 决策来源 | 规则、计算模块、经过准入的策略及模型辅助理解 | 指定版本的RL、规则或运筹策略 |
| 执行范围 | 当前身份获准调用的登记能力 | 隔离仿真、离线数据和影子比较 |
| 结果 | 任务状态、实际变化、原始回执、可核对报告 | 模型来源、状态动作奖励、性能曲线、失败样例和实验包 |
| 不合格处理 | 暂停、拒绝、重试可重试步骤或转人工 | 保留失败候选及原因，使用经验证的基线或停止 |

两种模式共用身份、硬约束、预算和审计。策略的奖励分数不能覆盖权限与安全条件。每个任务固定模式、模型、数据和环境版本；执行过程中切换模式须生成新计划并重新检查授权。

拟建的统一任务路径：

```text
用户或移动端
    ↓
小懿理解目标并选择模式
    ↓
能力目录与依赖计划
    ↓
数据核验和业务约束
    ↓
企业受控流程 或 策略研究实验
    ↓
五个下游系统适配器
    ↓
原始回执、结果核验、审计和任务报告
```

“完成所有相关任务”将落实为版本化能力清单：每项任务都有输入、目标系统、作用范围、前置条件、动作参数、权限、验收结果和恢复方法。参数不完整时提问；未登记的能力返回缺口，进入后续开发清单。

## 4 逐步实施与阶段验收

### 步骤0 保存六系统现状并建立回退基线

记录每个项目的路径、Git状态、未提交修改、版本、启动方式、依赖和关键配置。保留现有生成模型、嵌入模型、LoRA、知识库、索引、数据和策略文件。备份任务数据库及需要迁移的数据，记录源文件哈希；隔离分支或工作区必须保留当前未提交工作。

交付：六系统基线清单、现有功能清单、关键文件清单和经过演练的恢复步骤。

验收：原有问答、检索、训练入口、联动、报告、启动与移动端功能建立可复现基准；新增功能关闭时能够回到该基准。现有故障单列记录，不把旧故障包装为新功能通过。

### 步骤1 建立统一能力目录

逐项读取各系统实际接口和操作，登记读取、计算、仿真变更、任务管理、训练和审批等能力。每个动作定义严格参数、单位、范围、前置状态、权限、超时、结果结构、幂等支持及补偿方式。标明哪些当前可用、需要补适配、只能展示或尚未实现。

交付：版本化能力清单、系统职责表、接口契约和覆盖矩阵。

验收：目标系统的能力能被实际查询和调用；页面已打开不等于动作已执行；每项任务的成功判定对应真实业务回执。

### 步骤2 对齐数据与联合场景

定义统一任务、场景、港口、码头、船舶、设备、策略和实验标识。时间采用带时区的事件时间，并分别保留采集、发布、决策和执行时间。明确kW与kWh、速度、距离、坐标、成本和碳排口径。保留真实观测、预测、代理、模拟和默认值的来源标签。

不同地点和历史日期的数据只有经过显式场景映射才能进入联合推演。同一任务保存一组时间可对齐的快照及版本；航行、港区和能源的不同仿真步长通过事件接口衔接。

交付：联合场景契约、实体映射、时间与单位转换、质量检查和来源记录。

验收：地点冲突、单位不符、数据过期、缺失关键字段和快照不一致时，系统明确暂停相关结论或执行。观测的采集或发布时间晚于决策时刻时，拒绝将它作为当时已知信息；预测允许具有未来目标时间，但发布时间必须符合决策时刻要求。

### 步骤3 完善共用任务执行底座

在现有Harness上增加有依赖关系的步骤、结果绑定、资源预算和可恢复状态。先读取和检查前置条件，再执行获准动作，最后读取实际状态进行验证。只读步骤可有限并行，同一业务对象的写入采用版本检查和资源锁。

写入前保存意图和幂等标识。超时后先查询回执，执行状态未知时转为待核查，禁止盲目重复。恢复使用补偿动作并核验当前版本；恢复配置不等于倒退业务时间。跨系统部分成功应明确标记，不声称具有分布式原子事务。

交付：统一任务状态机、步骤依赖、执行记录、恢复及补偿机制。

验收：进程重启、重复请求、步骤失败、取消和服务失联都能得到可解释状态；已确认执行的动作不会因重启被重复下发。

### 步骤4 完成企业受控模式

提供态势汇总、风险复核、交班、情景比较、参数试算、联合调度和异常处置模板。模型生成或调整步骤时，仍需符合能力目录和模板要求。高影响动作按已配置权限与审批流程执行；审批绑定具体计划、参数、版本和有效期，身份由服务端认证取得。

报告使用实际工具结果和原始回执，区分模型解释、规则计算和确定性报告。已有数字、来源和约束检查继续保留，并为每类任务增加业务验收条件。

交付：企业模式模板、计划预览、审批、执行、结果报告和回退入口。

验收：正常任务完成；参数不足会澄清；错误或过期证据不会被写成合格结论；越权动作被拒绝；报告可追溯到执行记录。

### 步骤5 隔离测试预训练任务规划模型

下载固定版本的AgentCPM-Explore Q4_K_M候选并核对本地哈希、许可证和提示格式。放入独立模型目录，通过独立服务和模型路由接入，不覆盖原生成模型。验证推理运行时、结构化输出、工具调用解析、中文指令及上下文预算，必要时编写格式适配器。

建立相同的港航任务集，对比原模型和候选的任务成功率、参数错误、虚构工具、证据错误、时延、Token和内存。模型卡的长上下文和公开基准能力不自动成为本机配置。

交付：模型登记、独立启动配置、格式适配、对比报告和回退配置。

验收：候选满足声明任务的功能和资源标准后才启用；候选故障时原问答和企业受控路径仍可使用。若收益不足，保留实验结果并继续使用原模型。

### 步骤6 修正RL环境并审计已有策略

消除读取未来真实记录的趋势特征，采用截至决策时刻的历史信息，或带发布时间的预测。审计数据划分、归一化、参数校准、终止条件、动作掩码、奖励、终端储备和指标来源。环境变更后更新版本，旧模型保留并标记兼容状态。

逐个核对小懿及下游系统已有检查点、训练日志、数据、状态和动作定义。需要重新训练或重新评测的模型明确列出；过去报告作为历史证据保存。

交付：修正后的环境契约、泄漏检查、策略来源表、兼容矩阵及复验报告。

验收：决策只读取当时可获得的信息；训练和验证用于模型选择，封存测试数据不参与调参；旧模型不会在接口变化后被静默复用。

### 步骤7 验证开源业务策略并接入一个完整子场景

优先测试RouteFinder的运输任务场景；如果异构多车任务更匹配，则采用PARCO HCVRP候选。先在发布方支持的问题上复现推理，再建立港区任务转换，最后在小懿研究工具中调用。

输入转换必须保留任务量、车辆容量、服务时间、时间窗及支持的距离定义。港区真实路网、单向通行、禁行区、车辆冲突和能源限制由独立验证器检查；模型不支持的关键约束不能靠静默丢字段处理。车辆路径模型只解决相应运输子问题，船舶操纵与避碰调用独立海事能力。

交付：一个可运行的预训练策略工具、输入输出适配、规则或运筹基线、仿真回放和适用范围说明。

验收：每个输出动作能映射回原任务；约束检查通过；不支持的实例明确拒绝。是否进入业务模式由基线比较及准入条件决定。

### 步骤8 按需训练小型业务策略

仅在已有策略或开源候选不满足任务要求时进入本步骤。先固定业务问题、环境版本、指标、基线和预算；小型离散任务可沿用表格RL，只有任务复杂度和资源允许时再选择DQN、PPO、SAC或其他合适方法。

采用多个训练种子，按时间、场景或港口划分训练、验证与测试。校准和模型选择只使用训练及验证数据。记录全部实验，包括失败、未收敛和劣于基线的候选。训练任务独立运行、可取消，并限制CPU、内存、时长和磁盘使用。

交付：配置、数据版本、训练曲线、检查点、验证选择记录、封存测试结果和失败分析。

验收：模型可复现且满足预定准入条件。未通过时保留在研究目录，企业模式继续使用合格基线。额外付费算力或大模型训练另列具体预算，不随本地小策略训练自动启动。

### 步骤9 建立RL策略研究模式

让小懿将研究指令转换为有限实验计划：目标、数据、环境、基线、候选、随机种子、预算、指标与结束条件。提供候选查询、策略推理、批量评测、比较和实验导出工具。研究任务默认调用已有模型；训练是独立的显式操作。

同一业务问题使用相同初始状态、外生输入、约束和评测窗口。各策略拥有独立环境实例，并分别演化状态。规则、PID、运筹和MPC等基线按实际适用性选择，比较时具有相同的信息可见范围，并报告计算预算。

交付：实验面板、State/Action/Reward轨迹、模型与数据版本、曲线、比较表和复现包。

验收：能展示RL改善、无改善和被拒绝三类结果；结果同时报告原始业务指标、约束违反、可行率、耗时和样本数。置信区间与显著性结论必须有明确统计方法及足够实验依据。

### 步骤10 补齐五个下游系统适配器

| 下游系统 | 需要落实的动作和回执 |
| --- | --- |
| 数字孪生 | 态势读取、资源和场景评估、获准的仿真计划应用、状态复核、恢复 |
| 能碳 | 读取、预测、候选比较、决策、现有岗位审批、模拟执行、执行后能量与成本核验、回滚 |
| 马六甲 | 场景读取与调整、交通及到港事件、模型推理、模拟决策、执行与审计 |
| 航行模拟器 | 场景加载、路线或任务参数、启动、停止、进度与结果；核对文件桥的请求对应关系和过期条件 |
| 移动端 | 提交任务、查看计划、按身份处理审批、停止请求、查看实际回执和原系统入口 |

身份、作用范围和原系统已有审批链由适配器保留。移动端共享同一个任务编号和权限来源，避免形成第二套互相冲突的任务状态。

交付：五个适配器及各自契约测试、健康状态、动作清单和回执样例。

验收：每个登记动作在对应系统产生可观测变化或明确的计算输出；离线和不支持的动作显示具体原因，不用本地合成回执冒充下游成功。

### 步骤11 实现跨系统联合任务

先建立一个所有系统均有明确职责的联合场景：天气或拥堵改变航行与到港时间，航行模拟器验证适用场景，数字孪生计算港区资源与负荷需求，能碳评估供能方案，移动端处理任务与回执，小懿汇总和调度流程。

按依赖传递结果，不把同一句话广播给所有系统。资源、服务能力或能源约束冲突时，修改候选并进行有限次迭代；达到预算仍不可行，则返回冲突约束和可选调整。并非每项日常任务都需要调用全部系统。

交付：联合任务模板、数据传递图、约束协商、执行与补偿流程。

验收：至少一条联合场景完成六系统真实操作与回执对齐；任一关键前置步骤失败时，依赖它的执行步骤停止，其他已完成步骤保留实际状态。

### 步骤12 完成统一网页与移动交互

在小懿增加模式选择、任务列表、步骤进度、系统状态、待处理审批、结果证据和研究实验视图。保留原有菜单及各系统入口。展示当前模式、模型、策略、数据时间、场景和操作范围。

演示提供明确的下一步、重试和重置按钮，每步等待可见回执后推进。移动端与网页展示同一任务；停止入口独立于大模型推理，停止后核验各系统实际状态。

交付：网页与移动端任务中心、两种模式界面和可单击推进的演示流程。

验收：真实点击完成闭环，刷新和返回后状态一致；窄屏可用；未完成的步骤不会提前显示成功；原有操作入口继续工作。

### 步骤13 完成故障与资源测试

覆盖服务未启动、错误服务占用端口、模型超时、数据过期、参数越界、拒绝审批、身份越权、回执丢失、重复请求、进程重启、并发冲突、部分成功、取消和补偿失败等情况。

记录各任务CPU、内存、磁盘、Token、运行时长和事件时间。采用有界并发和任务队列；研究训练降低优先级或排队，保证用户操作及企业模式的资源。对长耗时任务明确展示进度和剩余预算，不以伪造即时结果缩短演示。

交付：故障矩阵、恢复证据、性能报告和资源调度配置。

验收：各故障到达约定状态，未知执行结果不会自动当作失败重发；停止能在预定边界生效。性能标准在步骤0测得基线后固定，再按相同负载验收。

### 步骤14 回归原有功能并验证回退

运行各系统适用的后端、前端和接口测试，并进行真实浏览器与Godot、Flutter路径回放。逐项核对步骤0的原有功能和关键资产。新增数据库结构采用可追踪迁移，回退前先停止或处理活动任务。

交付：功能覆盖矩阵、自动化报告、界面截图或录像、原始回执、资产差异和回退演练记录。

验收：原有功能回归通过；新增功能开关关闭后恢复原路径；模型、知识库和数据变更均有明确记录；测试失败和未验证项不得从最终报告中省略。

### 步骤15 完成联合演示与研究交付

形成三条核心演示：企业任务自动完成、RL与常规策略公平比较、异常发生后的拒绝或回退。附一条六系统联合任务，展示每个系统实际承担的步骤和回执。

交付：演示按钮流程、讲解台词、架构说明、模型来源说明、研究复现包、部署与恢复说明。

验收：旁观者能够看懂指令、计划、调用、状态变化、策略差异和最终结果；可以独立复现至少一组实验。开源模型的原作者、适配代码和自行训练部分分别注明。

## 5 拟定的验收任务集

以下数量用于建立有限、可重复的项目验收，不代表开放世界任务可靠率。

| 验收方面 | 拟定要求 |
| --- | --- |
| 原有功能 | 步骤0形成的完整功能清单逐项回归，失败明确记录并修复或说明 |
| 企业模式 | 至少30条正常任务及10条参数不足、越权或证据异常任务，预先固定预期行为 |
| 五系统适配 | 每个登记动作至少有成功与主要失败路径证据；有状态动作核对执行后状态 |
| 联合闭环 | 至少1条完整六系统任务、2条部分系统任务，以及关键服务失联和资源冲突场景 |
| 策略比较 | 同条件比较合适的规则或运筹基线与RL候选；新训练候选原则上至少5个种子 |
| 预训练策略 | 权重固定时在多个实例或场景上评测；确定性推理不把重复同一输入当作独立样本 |
| 硬约束 | 约定验收集中违规方案全部被识别并拒绝；合格执行轨迹满足列出的约束 |
| 数据与版本 | 每次实验记录数据、环境、模型、代码、配置、种子、单位及时间范围 |
| 恢复 | 重启、重复提交、取消、未知执行结果及补偿失败均有测试 |
| 性能 | 固定场景测量普通问答及任务时延、内存和并发；以步骤0确定的预算进行准入 |
| 界面 | 实际点击回放，有状态变化与回执；重置、重试、停止和返回路径均可用 |
| 证据 | 报告指标可追溯，仿真收益与现场收益分别表述，研究失败候选保留 |

RL进入企业模式时，先满足全部硬约束，再检查预先声明的任务效果和计算预算。若以“优于基线”作为晋级条件，就必须在封存测试集上证明；未通过时，研究功能仍可完成，但该策略不能被宣传为业务冠军。

## 6 本机部署和训练安排

本次硬件核查为8核Intel Core i9、16GB内存、Radeon Pro 560X 4GB；小懿当前登记使用llama.cpp的CPU推理路线。新增模型和六系统同时运行的资源余量须实测，模型文件小不代表依赖、上下文和仿真进程的内存也小。

AgentCPM优先测试GGUF及现有推理协议。业务RL工作进程使用独立虚拟环境或独立服务，不直接升级小懿主环境。新版RL4CO依赖TorchRL等组件，而PyTorch官方已停止发布2.3及后续的macOS x86构建；因此开源检查点的本机可运行性是前置验收项。[PyTorch官方公告](https://dev-discuss.pytorch.org/t/pytorch-macos-x86-builds-deprecation-starting-january-2024/1690)、[RL4CO依赖](https://raw.githubusercontent.com/ai4co/rl4co/main/pyproject.toml)。

处理顺序是：验证兼容版本组合；如需独立Linux CPU服务或经验证的模型导出，记录部署要求后选择；若部署成本不合理，采用本地可复现的小型策略路线。不得为装入候选模型而破坏现有Python环境。

首期默认按需加载候选模型、限制重任务并发、将训练与演示分开。额外服务器、云端数据传输、付费GPU和大模型训练都不包含在默认本地执行预算中。步骤0及兼容性测试完成后才能给出可信工期和资源估算。

## 7 交付顺序与审核范围

建议按以下里程碑推进，每个阶段提供实际结果和未完成项：

1. 原系统基线与能力目录完成，可以清楚看到原有功能和接口缺口。
2. 共享执行底座与企业模式完成，先证明业务流程能稳定闭环。
3. 规划模型候选完成隔离对比，决定是否保留。
4. RL环境修正、已有模型审计和至少一个开源策略接入完成。
5. 对缺口按需训练小型策略，完成可复现研究模式。
6. 五个下游适配及六系统联合任务完成。
7. 网页和移动端验收、故障恢复、资源测试、全功能回归与演示交付完成。

用户本次审核的是上述整体路线、两种模式职责、开源优先的选型顺序、兼容性与准入条件，以及六系统联合任务的验收定义。审核通过后才开始实施。后续Agentic RL训练可作为独立研究阶段：利用真实任务轨迹学习工具选择、重试和停止策略，配套新的训练预算与封存评测。

交付名称建议采用“小懿港航联合任务与策略研究平台”。“面向未来超级智能”作为长期方向，通过新增可验证的能力持续推进；本期完成程度依据能力清单、实验和真实系统回执评定。
